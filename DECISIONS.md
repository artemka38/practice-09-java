# DECISIONS.md

## Вариант

Номер варианта: 25.

### Часть А

Изменено правило R2 — неотрицательный остаток.

По варианту 25 после операции `decrease()` на складе должна оставаться
минимум 1 единица оборудования.

Если после уменьшения `quantity` становится меньше 1,
метод выбрасывает `IllegalArgumentException`.

Изменение выполнено в методе `StockItem.decrease(int q)`.

Условие варианта:

`quantity - q >= 1`.

Например, при `quantity = 5` вызов `decrease(4)` разрешён,
так как после операции остаётся 1 единица.

Вызов `decrease(5)` запрещён,
так как остаток стал бы равен 0.

### Часть Б

В класс `Warehouse` добавлен public-метод:

`addAlmostEmptyItems(Warehouse wh) -> List<StockItem>`.

Метод возвращает позиции склада,
у которых `quantity == 1`.

Для поиска выполняется цикл по `wh.items.values()`.

Для каждой позиции проверяется значение `getQuantity()`.

Если количество равно 1,
позиция добавляется в новый `ArrayList`.

Возвращается новый список,
поэтому внутренняя коллекция склада напрямую наружу не передаётся.


## Решение 1

### Формулировка

Проверку минимального остатка варианта 25
я разместил непосредственно в методе `StockItem.decrease()`.

Класс `StockItem` сам хранит поле `quantity`,
поэтому именно он должен контролировать допустимость его уменьшения.

Проверка выполняется до изменения значения.

Если `quantity - q < 1`,
выбрасывается `IllegalArgumentException`.

### Альтернатива

Можно было бы разместить проверку в `Warehouse.issue()`.

Перед вызовом `decrease()` склад мог бы самостоятельно проверять,
останется ли после выдачи минимум одна единица.

### Обоснование

Такой вариант хуже,
потому что правило остатка относится непосредственно к `StockItem`.

Если проверять его только в `Warehouse.issue()`,
кто-либо сможет напрямую вызвать `StockItem.decrease()`
и обойти ограничение варианта.

Размещение проверки внутри `decrease()`
обеспечивает единое правило для всех мест программы.

Кроме того, `Warehouse.issue()` остаётся проще:
он находит позицию и делегирует изменение остатка самой позиции.


## Решение 2

### Формулировка

Для хранения оборудования в `Warehouse`
используется `Map<String, StockItem>`.

Ключом является инвентарный код позиции.

Получение элемента выполняется через `items.get(code)`.

### Альтернатива

Можно было бы использовать `List<StockItem>`
и каждый раз выполнять цикл по всем элементам,
сравнивая `getCode()` с нужным кодом.

### Обоснование

`Map` лучше соответствует задаче,
потому что основной способ поиска позиции — по уникальному коду.

`HashMap.get()` в среднем работает за O(1).

При использовании `List`
потребовался бы линейный поиск O(n).

Кроме того, `Map` удобно поддерживает правило R1:
перед добавлением можно проверить `items.containsKey(code)`.

Таким образом, структура данных соответствует предметной задаче
и упрощает проверку уникальности инвентарных кодов.


## Ответы на контрольные вопросы

### Вопрос 1

Какая проверка в этой работе защищает программу
от наиболее вероятной ошибки входных данных и где она расположена?

Одной из наиболее важных проверок является проверка уникальности
инвентарного кода в методе `Warehouse.addItem()`.
Перед добавлением новой позиции выполняется проверка
`items.containsKey(item.getCode())`.
Если такой код уже присутствует в `Map`,
выбрасывается `IllegalArgumentException`.
Эта проверка реализует правило R1.
Она важна потому, что инвентарный код используется
как уникальный идентификатор оборудования.
Если разрешить несколько позиций с одинаковым кодом,
приход, выдача и поиск оборудования могут работать с неправильной позицией.
Использование `Map` позволяет выполнять такую проверку просто
и не допускать появления дубликатов в каталоге склада.


### Вопрос 2

Какой метод или класс содержит ключевое бизнес-правило
и почему оно размещено именно там?

Одно из ключевых бизнес-правил находится
в методе `StockItem.decrease()`.
Этот метод контролирует уменьшение остатка оборудования.
В базовом варианте он не позволяет количеству стать отрицательным,
а в моём варианте 25 после списания должна остаться минимум одна единица.
Правило расположено именно в `StockItem`,
потому что этот объект хранит собственное поле `quantity`
и отвечает за корректность его изменения.
`Warehouse.issue()` не изменяет количество напрямую,
а вызывает `decrease()`.
Благодаря этому правило невозможно обойти,
даже если метод `decrease()` будет вызван
из другого места программы без использования `Warehouse`.


### Вопрос 3

Как Activity-диаграмма отражает
один конкретный участок вашего кода?

Activity-диаграмма отражает последовательность действий
в методах `Warehouse.receive()` и `Warehouse.issue()`.
Например, блок поиска позиции по коду
соответствует строке `items.get(code)`.
Следующий блок проверяет,
существует ли найденная позиция.
Если объект равен `null`,
выбрасывается `IllegalArgumentException` по правилу R9.
Для операции `issue` затем выполняется проверка допустимости уменьшения остатка
через метод `StockItem.decrease()`.
В моём варианте 25 эта проверка также учитывает минимальный резерв 1.
После успешного изменения количества
в список `movements` добавляется новый `StockMovement`.
Таким образом, блоки диаграммы соответствуют этапам реального алгоритма.


### Вопрос 4

Какое изменение требования в этой работе
должно затронуть минимальное количество классов и почему?

Примером является изменение минимального остатка оборудования.
В моём варианте 25 минимальный резерв равен одной единице.
Это правило находится в методе `StockItem.decrease()`.
Если в дальнейшем минимальный резерв потребуется изменить,
основная бизнес-логика должна изменяться только в `StockItem`.
Класс `Warehouse` при этом продолжит вызывать тот же метод `decrease()`
и не должен знать детали проверки остатка.
Такое разделение ответственности уменьшает количество изменений
и вероятность появления ошибок.
`StockItem` отвечает за собственное количество,
а `Warehouse` отвечает за хранение позиций
и выполнение складских операций.
Поэтому изменение правила остатка локализуется в одном классе.


## Фрагмент кода для анализа

Антипаттерном является хранение позиций в `List<StockItem>`
и линейный перебор всех элементов для поиска нужного инвентарного кода.
Такой поиск имеет сложность O(n), поэтому при большом количестве оборудования
он менее эффективен, чем `Map.get(code)`, который для `HashMap`
в среднем выполняется за O(1).
В данной работе позиции хранятся в `Map<String, StockItem>`,
поэтому правильным решением является получение позиции через `items.get(code)`;
это также удобно для правил R1 и R9, связанных с уникальностью
и существованием инвентарного кода.
